# Protein Dispenser — Digital Twin, 3D Model & Control PCB

Engineering package for a **protein-powder vending machine**: a functional digital
twin, an interactive 3D model of the cabinet interior, a fabricable KiCad control
PCB, and system documentation. Built directly from the real machine at the
installation site.

> **Live site (Vercel):** the dashboard, 3D view, wiring diagram and schematic
> render as a static site. When hosted there is no simulator behind the page, so
> the pages fall back to a **demo telemetry snapshot** generated from the same
> machine model. Run the twin locally for live behaviour.

### The machine (modeled from the real unit)

- **5 powder hoppers** — Whey Isolate, Cocoa, Creatine, Oats, Vitamin; 1.5 kg each,
  3.1 g/rev auger screws metered by revolution count.
- **Water system** — 20 L tank, hot-water boiler (setpoint 65 °C) and a chiller
  loop (setpoint 4 °C) with condenser + compressor.
- **Actuators** — 8 relays (5 auger motors, cup drop, hot water, cold water),
  an SSR-driven heater, a compressor contactor, condenser fan, mixer and turntable.
- **Electronics** — 12 V (LRS-100-12) and 24 V (LRS-100-24) supplies, control MCU,
  relay board, SSR, and safety interlocks (door switch, cup sensor).

## Quick start

Requires **Node.js 18+**. No dependencies to install — the project is pure Node
standard library.

```bash
npm start            # twin server -> http://localhost:5177  (dashboard)
npm test             # run one full brew cycle against the model
```

Then open:

| URL | Page |
| --- | --- |
| `http://localhost:5177/` | Operator dashboard (live) |
| `http://localhost:5177/three/index.html` | 3D internal view (live) |

The server pushes telemetry at 10 Hz over a raw WebSocket and exposes a REST API
(`/api/power`, `/api/brew`, `/api/refill`, `/api/fault`, `/api/clear`, `/api/door`).

## The 3D internal view

An interactive model of the cabinet interior, built procedurally (no external
model files) and driven by the live telemetry stream.

**View modes:** Explode (parts pull out radially) · X-ray skin · Door swing ·
Flow paths (powder / hot / cold routes)

**Focus filters:** Electrical · Thermal · Powder — dim everything else and fly
the camera to that subsystem.

**Live binding:** relays light up, hopper cones shrink with level, boiler/SSR
LEDs glow when heating, the compressor and condenser fan run when chilling, and
the mixer shaft and cup turntable spin. Click any part to identify it.

## The control PCB (fabricable)

[`hardware/pcb/ProteinDispenser_Controller.kicad_sch`](hardware/pcb/ProteinDispenser_Controller.kicad_sch)
is a real KiCad 7 schematic — 56 symbols, 63 named nets — generated by a script
and structurally verified, ready to open in KiCad and send for fabrication.

```bash
npm run gen:schematic       # regenerate the .kicad_sch from source
npm run check:schematic     # structural + netlist checks (10 checks)
npm run render:schematic    # render the schematic to SVG for browser preview
```

The schematic renders to [`schematic_preview.html`](hardware/pcb/schematic_preview.html)
without needing KiCad installed. To **edit** the schematic you need KiCad itself.
Run a full **ERC** in KiCad before fabrication — the automated checks cover
structure and connectivity, not electrical-rule clearance.

## Deploying to Vercel

The site is a static bundle assembled from the twin dashboard, the 3D view and
the engineering docs.

```bash
npm run build        # -> public/  (static site + demo telemetry)
```

`vercel.json` configures Vercel to run the build and serve `public/`:

| Route | Page |
| --- | --- |
| `/` or `/dashboard` | Operator dashboard |
| `/view3d` | 3D internal view |
| `/wiring` | Wiring diagram |
| `/schematic` | Control-PCB schematic |

**Deploy:**

```bash
npm i -g vercel
vercel            # preview deployment
vercel --prod     # production deployment
```

> **Why the twin server isn't hosted:** Vercel runs serverless functions that
> cannot hold a long-lived WebSocket, and a serverless simulator would reset
> between requests. So the twin runs locally, and the hosted pages use
> `public/demo-state.json` — generated from `twin/machine.js` at build time — to
> render realistically offline. Point the pages at a public twin URL later if you
> host the server somewhere persistent (a VPS, Fly.io, Railway, etc.).
